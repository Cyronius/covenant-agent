# R10 — the register region on 42 unseen worlds, and an exam a style detector can pass

**Date:** 2026-09-22, analysis revised 2026-09-23. **Hardware:** one RTX 3090,
RunPod community, $0.22/hr, 1.87 h — **$0.41**, plus ~$0.06 burned on four broken
4090s (§6). **Cache:** `models/tiny/data_cache_ho42_reg`, structural binding,
`s5_plain` train / `s5_holdout_both` holdout, both regenerated with 3b's
two-segment references and step 4's register region. **One arm, one seed:**
`ar`, seed 0, 12 epochs, batch 64, 5,052 steps, d=256, **9,382,966 parameters**
— the same size as R9's model (9,386,814). **Scored on the laptop** (the sandbox
needs Node).

Tier 1 of a four-tier plan: the cheapest run that says anything about a trained
model on this cache. Not a replacement for R9's both-arms × three-seeds shape.

**Revision note (2026-09-23).** The first version of this file said the model
was 19% larger than R9's, that gate 2 was met, that pausing "buys 0.6 points",
and that the register region costs 2.5 GB of VRAM. All four were wrong: R9 was
also 9.39M; gate 2 was compared on the wrong unit; the pause figure pooled
levels with very different pause rates; and the VRAM tracks the wider cache.
The corrected versions are below, alongside three new measurements (§8–§9).

## 1. The headline

| half | goal | `same_tool` | shape-only null | margin | `decoy_called` |
|---|---|---|---|---|---|
| plain | **70.7%** | 87.7% | 100.0% | — | — |
| decoyed | **42.1%** | 54.7% | 43.6% | **+11.1** | 43.8% |

Single-segment rows only, which is the like-for-like against R9:

| | R9 (9.39M, 3 seeds) | R10 (9.38M, 1 seed) |
|---|---|---|
| plain goal | 70.4% | **70.3%** |
| decoyed goal | 46.0% | **40.4%** |
| margin over shape-only | +19.2 | **+12.0** |

Plain is unchanged to a tenth of a point. The decoyed half lost 5.6 points of
goal and 7.2 points of margin.

**That drop is not attributable.** Same width and depth, but the cache changed
in six ways at once — the `EFFECTS` header retired (1b; keyword rows 62 → 54),
the property migration (1e), decoys on by default (1f), L21 answering rows (2b),
3b's two-segment references, and the register region — and the layout widened
(tool rows 50 → 54, field rows 23 → 28). One seed against three.

**And the margin itself is not yet evidence of reading** — §8 shows a
description-only classifier separates real tools from decoys perfectly, so a
positive margin is what a model that learned "reject template-sounding
descriptions" would also produce.

Training-world fit, for scale: test split **95.1% goal, 99.5% compile**. The
95.1 → 70.3 step is the cost of an unseen world; 70.3 → 40.4 is the cost of
making the signature ambiguous.

## 2. Gate 2 is not met

Step 4's gate: goal success on **two-segment tasks** within five points of
one-segment tasks **of the same level**. A two-segment task needs both of its
segments right. Scoring each segment with the reference supplied for the other
and requiring both to reach the goal — the closest proxy this run has to the
live loop — on the plain half:

| level | two-segment tasks, both segments right | one-segment rows | gap |
|---|---|---|---|
| L5 | 16/40 (40%) | 54% (n=48) | **−14** |
| L7 | 19/35 (54%) | 46% (n=56) | +8 |
| L11 | 11/21 (52%) | 73% (n=66) | **−21** |
| L10 | 49/87 (56%) | — | two-segment only |

Decoyed half: L5 25% vs 17% (+8), L7 34% vs 11% (+23), L11 43% vs 68% (**−25**).
The gate fails on L5 and L11 on the plain half, and on L11 on both. Samples are
small (21–87 tasks a level).

The first version of this file compared *segment rows* — each segment scored
with the other half handed to it — against one-segment rows and reported the
gate met. That was the wrong unit: it counts a task whose first segment fails
and whose continuation succeeds as half a success.

The split by segment still says something:

| | plain | decoyed |
|---|---|---|
| first segments (`#s0`) | 58.5% | 34.4% |
| continuations (`#s1`) | **86.3%** | **65.0%** |

The continuation is the easy half — `FOREACH r1 -> r2 ; CALL T11 r2 ; STOP`
against a register region that says `r1` holds four cards is a smaller problem
than a whole program. The first segment is where two-segment tasks are lost.

**The live number is not in this run.** `#s1` is scored with a correct first
segment and the reference's registers (`corpus._replay`); `play.py` is the live
loop, and it needs the weights (§7).

## 3. The pause: learned where it is structural, and inconclusive beyond that

Every one of the 183 first segments has a reference ending in `PAUSE`. What the
model did:

| level | paused | |
|---|---|---|
| L10 | **86/87 (98.9%)** | the pre-3b recipe: cut a filter-then-act program after the filter |
| L11 | 11/21 (52%) | |
| L7 | 14/35 (40%) | |
| L5 | 10/40 (25%) | |
| all | 121/183 (66.1%) | |

The structural pause is learned nearly perfectly; the data-dependent pause 3b
added about a third of the time. The CPU preview (`SECOND_TURN.md` §5) saw 2 of
28 at 1.6M parameters and 3,000 rows; here it is 35 of 96 at 9.38M and 27,000
rows. Size and data moved together, so this does not say which moved it.

**Does pausing pay?** Goal success of first segments, by whether the model
paused, *within* each level (plain half):

| level | paused | did not pause |
|---|---|---|
| L5 | 6/10 (60%) | 18/30 (60%) |
| L7 | 6/14 (43%) | 13/21 (62%) |
| L11 | **7/11 (64%)** | **4/10 (40%)** |

The first version pooled these and read 58.7% vs 58.1%, "pausing buys 0.6
points". That pooled number is Simpson's paradox: the paused group is 71% L10
and the not-paused group 84% L5/L7. Within level the answer differs by level,
and on L11 — the level 3b redesigned so a one-shot program would stop being
free — pausing looks worth ~24 points on both halves. With 10–35 rows a cell,
none of this is conclusive, and teacher forcing hands the paused arm a correct
continuation for free, so this comparison cannot settle the question either
way. The live loop can.

For scale, the training corpus: 9.0% of `s5_plain` rows pause, and about half
of those (179 of ~340 a shard) are L10.

## 4. What the run cost, in VRAM and time

| | R9 (4090) | R10 (3090) |
|---|---|---|
| tool + field rows in the cache | 50 + 23 = 73 | 54 + 28 = 82 |
| peak VRAM at batch 64 | 18.9 GB | **21,450 MiB** |
| s/step | 0.53 | 0.62 |
| train wall time | ~45 min | 50 min |

**The VRAM increase tracks the wider cache, not the register region.** Per-
process VRAM on this model is set by the schema lines every row carries
(`runpod-deploy` memory, R9): 82 rows against 73 is +12%, which predicts
~21.2 GB from R9's 18.9 — the measured figure. The register region adds 8 lines,
almost all padding. The step-time difference is confounded the same way, so
what the card substitution cost is not measured here.

Where the memory goes, measured on the laptop by counting what autograd saves
for backward (details in `.claude/plans/description-reading.md` §2): ~87% is
hidden state in the per-line encoder, and **88% of the line encoder's token
positions are padding** — tool lines average 28 real tokens of 80, and 41% of
the 54 tool rows hold a tool at all.

Slot accuracy on the val split (training worlds) at the last evaluation:
`acc_tool` 99.3%, `acc_field` 95.7%, `acc_const` 100%, **`acc_reg` 100%** over
1,087 register slots, `val_loss` 0.0130 and still falling slightly.

## 5. Two defects found, both of the same shape

**Every continuation was dropped at the scoring step.** `evaluate.py` looked a
generated row up by `task_id` in `rows.pkl`, which is keyed by whole tasks, so
`foo#s0` and `foo#s1` missed and hit a bare `continue` — 183 paused tasks, 366
rows, no score and no counter. The first scoring of this run therefore produced
a single-segment-only holdout number, silently, and gate 2 was absent from it.
Fixed: `evaluate.py` resolves the base task, replays for a continuation's
context, scores the whole task with the generation in its own segment's place,
and counts `unscorable` rows out loud.

**The combined holdout was assembled with `cat`.** Both halves are the same
8,000 tasks with the same ids; the decoyed half has to be re-identified
(`+decoy`, R9.md §7) or every id appears twice. It did, 8,757 times, and the
cached tensor and the row a scorer looked up were then different tasks with
different tool counts — which reads as a broken encoder. Caught by `selftest.sh`
(holdout round trip 2/20), which is the whole reason that check exists. `prep.py`
now refuses a holdout corpus with repeated ids, and `gen_s5_holdout.sh` carries
the real assembly instead of the word "CONCATENATION".

Both are the same defect as 92a6f54, one stage further down each time:
everything downstream of `corpus.load` was written before continuation rows
existed, and each stage fails silently in its own way.

## 6. Renting the pod

Four community 4090s could not train. Each one: `nvidia-smi` sees the card,
`torch.cuda.is_available()` returns False. On the one diagnosed in full,
`libcuda.so.1` was present and matched driver 580.126.09 and NVML worked — the
container had been handed the host's GPU index 4 as `/dev/nvidia4` with no
`/dev/nvidia0` and an empty `/dev/nvidia-caps`. Host-side device injection, not a
missing library, not fixable from inside. Three further create calls failed on
RunPod's side (`INTERNAL_SERVER_ERROR` twice, `SUPPLY_CONSTRAINT` once). The
community 3090 worked first time.

For `pod.md`:

- **Verify `torch.cuda.is_available()` before uploading anything.**
- **`scp` cannot go through the proxy.** It requires a PTY and refuses the sftp
  subsystem, so `scp` and `scp -O` both fail. Some hosts publish a direct TCP
  port (one of the broken 4090s did); the 3090 host did not. The transfer that
  always works is `runpodctl send` on one side and `runpodctl receive <code>` on
  the other; `runpodctl` is at `/usr/bin/runpodctl` in the pytorch image.

## 8. The decoyed exam can be passed without reading the request

**The tool name never reaches this model.** A schema line is
`{sym} ({params}) -> {ret} [{effect}] :: {desc}` (`harness/context.py:382`).
R9 §3's open question, "names or descriptions?", does not exist for the tiny
planner. Inside a signature group the only separators are the effect tag and
the description, and the effect tag separates the real tool from every rival in
**5 of 3,315** reference calls (`models/tiny/decoy_signal.py`). So it is the
description or nothing.

**The input carries the signal.** A real description and a same-effect rival
differ by a median **21 tokens** under the cache's BPE (token Jaccard 0.14).

**But a request-blind reader can pass the exam.** Training saw **0 of 30,000**
decoyed rows; exam decoys are written from a fixed template bank
(`harness/decoys.py:265`) that ignores the theme's `desc_style`, while real
descriptions are authored per theme; and the answer is never a decoy. Three
measurements of what that allows:

| | |
|---|---|
| a bag-of-words classifier on the **description text alone**, trained on 21 exam worlds, tested on the other 21 | **AUC 1.000**, accuracy 94.1% (majority class 77.2%) |
| its strongest decoy features | "rather than", "copy of", "records", "it" |
| words that are a single token under the 4,096-piece BPE (trained on training lines) | training descriptions 92.2%, held-out real 83.8%, **bank decoys 72.8%** |

And the model's choices track a request-blind cue much more than the one
request-side cue measured (`decoy_signal.py`): accuracy moves 15.1 points with
whether the real description looks more like training text than its twins
(56.0% vs 40.9%), and 1.6 points with whether it shares more words with the
request (54.6% vs 53.0%). Word overlap is a crude proxy for reading, so this
does not show the model ignores the request. It shows that the +11.1 margin —
and R9's +19.2, built the same way — cannot be read as "reads descriptions
against the request" until the decoys stop being detectable on their own.

**How hard is the decision when read honestly?** An off-the-shelf 33M
retrieval encoder, `bge-small-en-v1.5`, choosing among the same twins by
request-to-description cosine with no training on this data, picks the real
tool **65.9%** of the time against 42.0% for a uniform guess inside the group
(3,427 decisions, `models/tiny/teacher_twins.py`). R10's `same_tool` on these
calls is 54.0%. That encoder was never shown this exam's decoys, so its number
is reading, not style.

## 9. Twin geometry: the collapse starts in the line encoder

`models/tiny/twin_geometry.py`. R10's weights are gone, so this runs on the
only surviving checkpoint of this architecture: the tier-0 CPU model
(`SECOND_TURN.md` §5) — **d=128, 1.6M parameters, 3,000 training rows, epoch
10 of 14, never trained on a twin.** A proxy, not R10. Each of its held-out
tasks gets one twin per called tool (swapped in for an uncalled tool, so the
tool count stays at the layout's 22) and the reference slots are
teacher-forced: 104 tasks, 236 real/twin slot pairs.

Twin closeness at each stage the pointer's input passes through, bank twins
(median; model picked the real tool | picked the twin):

| stage | cos(real, twin) | twin distance ÷ unrelated-pair distance | dimensions used (participation ratio, of 128) |
|---|---|---|---|
| 1 line encoder output (CLS pool) | 0.928 \| 0.965 | 0.37 \| 0.26 | **4.3** |
| 2 after the schema graph pass | 0.955 \| 0.983 | 0.32 \| 0.20 | 4.0 |
| 3 after the turn encoder (request mixed in) | 0.974 \| 0.991 | 0.32 \| 0.17 | 5.5 |
| 4 pointer key | 0.989 \| 0.997 | 0.30 \| 0.17 | 3.6 |

With real training-world descriptions as twins instead of the bank, the same
shape: at the line encoder the twins the model gets right sit at 0.65 of an
unrelated-pair distance, the ones it gets wrong at 0.19.

What this says:

- **The collapse is already present at the first stage.** The line encoder's
  output uses about four of its 128 dimensions, and the pairs the model will get
  wrong are already mapped together there. Later stages tighten it a little;
  none creates it. The turn encoder — the first place the request meets the
  tools — does not pull twins apart.
- **It is organised around type shape.** Over 6,804 pointer keys from 92
  worlds, 19 abstract signature shapes (`ID:x -> OBJ:x [M]` and so on) explain
  54% of the variance; the world explains 3.5%. A training set whose tools are
  100% signature-unique rewards exactly that: a handful of directions picks the
  right tool every time there, and nothing pushes description content into the
  geometry.
- **The query adds a second, smaller problem.** At the pointer, on a failure
  the query points slightly *against* the direction separating the twins
  (cos −0.13; +0.29 on successes).
- **For contrast**, `bge-small` keeps the same kind of pairs at cosine 0.71
  against 0.58 for unrelated tools; this line encoder has them at 0.93–0.97
  against 0.61.

That width is not the binding constraint is an inference, not a measurement:
this model uses ~4 of 128 dimensions, and a wider one trained on the same
objective has no reason to use more. The test is the same command on a d=256 or
d=512 checkpoint trained with twins in the data.

Caveats: small, short-trained, never saw a twin; 236 pairs; teacher-forced. With
borrowed twins it picked the twin *less* often than with bank twins (21% vs
26%), the opposite of what a familiarity prior predicts — but borrowed
descriptions carry other worlds' nouns, which makes them easy to reject, so that
is not a clean test of §8.

### 9b. What the teacher says about splitting the line, and about width

`models/tiny/teacher_twins.py --view ... --squeeze ...`, the same 2,594 twin
decisions (first 1,500 decoyed exam tasks), `bge-small` zero-shot. Only the text
embedded per candidate changes:

| what the teacher embeds per tool | picks the real twin |
|---|---|
| description only | **65.0%** |
| the full line, as the tiny planner reads it | **56.1%** |
| signature only | 41.2% (chance ≈ 42%) |
| name only | 49.4% |
| name + description in one string | 60.7% |

Putting the signature into the same pooled vector as the description costs even a
well-trained encoder 9 points: twins' signature text is identical, so it dilutes
the part that separates them. Names carry some signal alone and cost 4 points
when folded into the description. Each part reads best in its own vector.

And the description distinction is low-dimensional. With the teacher's
embeddings projected onto principal components fitted on training-world text
only:

| dimensions | 384 | 256 | 128 | 64 | 32 | 16 |
|---|---|---|---|---|---|---|
| picks the real twin | 69.3% | 68.4% | 65.6% | 62.8% | 60.3% | 59.1% |

128 dimensions keep ~95% of what 384 can do, so a 128-wide encoder has room for
it; the d=128 proxy uses about 4. (Centring on the training-world mean alone
took the teacher from 65.0% to 69.3%.)

## 10. What to do next

`.claude/plans/description-reading.md` (v3, 2026-09-23): make the exam
unpassable without reading (theme-authored decoys, a detectability audit as the
gate); split the line encoder into small stages — signature and description,
possibly name — each with its own objective (contrastive with twins as hard
negatives, distillation from a small pretrained encoder), combined by a gate at
the pointer; pack the padding out; and bring the weights back from every run so
§9 can be measured on the real model.
