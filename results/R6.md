**Date:** 2026-09-10. **Plan:** `.claude/plans/spec-0.4.0.md` §8. **Model:**
Qwen3.5-0.8B, fresh LoRA (r=32, 2 epochs, same recipe as S1-S3) on the S4
typed corpus (`results/logs/gen_s4.sh`, `results/logs/train_s4.sh`) — the
same 62,841-row mix S3 used, rebuilt in the spec 0.4.0 surface (typed
constant letters, string kinds, schema enum constants, `MOST`/`LEAST`/

steps, no OOM, final train_loss 0.01282 (S3: 0.0117). Cost: training ~$14,
plus ~$3 lost to a dead pod (see §3) and ~$1 for eval — about $18 total.

## 0. Correction (same day, later): §1 scored the wrong surface

`eval_s4.sh` never passed `--symbols typed --enums --kinds`, and `run_a`
defaults to classic. Every row in `results/logs/s4_typed/` carries
`condition: A-grammar-task` with no `+letters+enums+kinds` suffix, and the
model's E-known outputs use `C` constants only (2,303 of them, zero typed
letters) — the grammar built from the classic symbol table forced them. So
a model trained on nothing but S/N/B/D/I letters, kinds and enum constants
was scored on prompts it had never seen. The HF/PEFT check in §2 built its
prompts the same way (its printed programs are all `C`-symbol), so it
confirmed the GGUF was faithful, not that the training had regressed.

A local CPU smoke on the first 100 E-known tasks with the flags on gave
97/100 (classic prompts on the same rows: 88; S3: 100), so the full suite
set was re-run on a pod (RTX 5090 community, $0.69/hr, ~50 min, under $1)
with `eval_s4.sh typed`, same fixed pruned GGUF. Files:
`results/logs/s4_typed/typed_surface/`. The local CPU run of the demo suite
matched the pod cell for cell (31/65, 0 abstains), so the two inference
stacks agree.

### 0.2 What is left of the regression: three failure classes

**E-known −3.2 (42 misses; S3 missed 10 of the same 1000).** 19 of the 42
are level 4 and 27 carry `adv:quantifier`. The pattern is one idiom:
"email the customer with the most closed tickets" →
`MOST r1 F7 -> r2 / CALL T4 r2.F9 S1` — a field access on the `MOST`
result, which is the customer's *id*, not the customer. `TYPE_ERROR
OBJ:<entity> ID:customer`, 14 of the 16 static errors. The corpus never
teaches the recovery: of 2,024 `MOST`/`LEAST` instructions in `sft_s4`,
2,016 are followed by `CALL T r S` (the winner's id passed straight to a
tool) and 8 by a re-fetch `FILTER`. E-known's argmax tasks need a *field*
of the winner (an email), which the S3 count loop produced for free
(`LET r6 -> r3` keeps the object) and `MOST` does not. A generator gap in
the argmax recipe, present in both the typed and classic corpora.

**Abstain control −16.25 (39 misses, all in two levels).** L11, 25 of 30:
the reference is a bare `ABORT NOT_FOUND`; the model writes
`ABORT AMBIGUOUS F4` (15) or `ABORT NOT_FOUND F6` (10), the latter a
`TYPE_ERROR` because a `NOT_FOUND` referent must be a constant. The corpus
pairs `NOT_FOUND` with an `S` referent after an `IF EMPTY` check (2,597)
and `AMBIGUOUS` with an `F` referent (1,232); it has 195 bare `NOT_FOUND`
aborts and zero `NOT_FOUND F`. When a task gives no list tool to check
with, the model reaches for the `F`-referent shape it knows. A corpus
distribution shift from §8's check-then-decline change, again in both
corpora. L18, 14 of 30: `two_id` note tasks ("delete the Handover note
from the HabitHive submission") where the model passes `NULL` for the
note id instead of listing and filtering — `CALL T11 I0 NULL`. S3 did
these 30/30; not yet traced to a recipe.

**E-foreign −2.2** was not broken down; it clears its bar.

### 0.3 What this changes

The typed surface is not the messenger for a broad collapse — there was
no broad collapse. The two remaining misses are recipe-level (the `MOST`
argmax idiom, the abort-referent distribution) and would show up in the
classic control too, since both corpora share the composites. The classic
control now decides a narrower question — whether the letters cost the
1–3 points on E-known/E-foreign that separate S4 typed from S3 — and that
is worth $14 only after the two recipe gaps are fixed, since fixing them
moves both arms. Order: fix the argmax recipe (re-fetch the winner when
the action needs a field), fix the bare-`NOT_FOUND` distribution, trace
L18, regen, retrain typed, and run the classic arm from the same regen if
E-known is still under 97.

`eval_s4.sh` now takes the arm and sets the flags. §3's GGUF bug and §4's
infrastructure notes stand. Sections 1, 2, 5 and 6 below are left as
written for the record; their numbers are the mismatched-surface numbers.

### 0.3b Both recipe gaps are closed in the generator (2026-09-12)

Neither was a new recipe; both were distributions.

**Argmax.** `_sample_extreme` always ended in an action on the winner, and
in the theme worlds that action takes the winner's *id*, so the re-fetch
branch fired only for `crm`'s send_email (8 of 2,024 rows). L4 now asks a
question 40% of the time - "which supplier has the most late deliveries?" -
whose answer is the winner's name, so the corpus teaches
`MOST -> FILTER id EQ -> FIRST -> GET` as the ordinary way to read a field
off an argmax. `data/gen/programs.py`, recipe `argmax_which`/`argmin_which`.

**Bare `ABORT NOT_FOUND`.** The L11 exam's 30 tasks name a record whose name
reached no constant - `constants` is empty on every one of them - so there
is nothing to filter on and no referent to name, and the bare abort is the
only faithful program. The corpus allocated the name every time it could,
which is why the model reached for `AMBIGUOUS F4`. L11 now leaves the name
unextracted 40% of the time.

Both fixes move the classic arm too, so the §0.3 order still holds: regen,
retrain typed, run the classic control only if E-known is still under 97.
The corpus that carries them is `results/logs/gen_s5.sh`, and in its 56,000
tasks:

| | S4 | S5 |
|---|---|---|
| `MOST`/`LEAST` rows | 2,024 | 1,934 |
| of those, re-fetching the winner | 8 | **798** |
| `ABORT NOT_FOUND`, bare | 195 | **1,168** |
| `ABORT NOT_FOUND`, with a referent | 2,597 | 1,496 |
| rows using `IN` (L19, new) | - | 2,664 |

Whether any of it transfers was the S5 eval's question, and the answer is `results/S5.md`: the argmax re-fetch and the bare abort both took (E-known 97.2, abstain control 99.2), and the recovery family did not.

### 0.4 The L18 NULL failure is fixed (2026-09-10, later)

§0.2 left L18 untraced: 14 of 30 `two_id` note tasks wrote
`CALL T11 I0 NULL` for a note id instead of listing the notes and filtering
by title. The cause was not the corpus, which never writes NULL — 0
occurrences in 62,841 rows. It was the harness. The per-task grammar
appended `"NULL"` to every operand class, required slots included, and the
typechecker treats NULL as compatible with every type, so on a task whose
note id exists in no constant and no bound register, NULL was the only
operand the grammar could emit for that slot, and it compiled clean.

Fixed in `core/typecheck.py` (a literal NULL in a required slot is
`MISSING_ARG`) and `harness/task_grammar.py` (typed required slots are built
without NULL; optional slots keep it). Plan and full rationale:
`.claude/plans/null-required-slot.md`; the same hole is what
`results/RPG.md` found independently.

Re-scored, same 30 L18 tasks, same pruned-fixed GGUF, same typed surface:

| L18 (n=30) | before | after |
|---|---|---|
| goal | 16 | **17** |
| programs containing NULL | 14 | **0** |
| tasks fixed / broken | — | 1 / **0** |

Modest on the scoreboard, and the shape of what is left matters more than
the +1. Of the 14 tasks that used to write NULL, one now writes the
reference's full form (list, `FILTER` by title, `FOREACH`, pass `r2.F0`) and
succeeds. The other 13 reach for the right shape and fail earlier: they
write `CALL T11 I0 r0.F0` — a register field read, which is what the
reference does — without binding `r0` first, so they now fail at compile
time as `UNBOUND r0` instead of failing opaquely in the sandbox. That is a
diagnostic a repair round can act on; this eval runs with `--repair 0`, so
whether the model can close the gap when told is the obvious next
measurement, and a cheap one.

**Measured 2026-09-12, same 30 tasks, same GGUF and surface, `--repair 1`:
19/30, with 22 of 30 compiling.** So being handed the diagnostic closes 2 of
the 13, not 13 of the 13. The model can act on `UNBOUND r0` sometimes; more
often it writes the same unbound read again. A repair round is worth its
second generation on this level, and it is not a substitute for a corpus
that teaches the list-then-filter form.

E-known and the other suites are unaffected: no reference program in
`data/r1_tasks.jsonl` or any `data/holdout/e_*.jsonl` contains NULL, and the
full test suite (221 tests) passes.

## 2. Ruled out: this is not the GGUF pipeline

Before trusting these numbers, I checked whether they were an artifact of
my own emergency surgery on the model file (§3). I reloaded the base model
and the LoRA adapter directly through `transformers`/`peft` — no GGUF, no
quantization, no pruning, no hand-rebuilt file — and scored a 60-task slice
of E-known through the same harness (`build` + sandbox), truncating
generation at the first hallucinated turn marker (unconstrained HF
decoding has no grammar to stop it at the program terminator, so it runs
on past `STOP`/`PAUSE` into fake continuation turns — a bug in the
diagnostic script, not the model, worth a full paragraph in case anyone
reruns this: truncate at `\nuser`/`\nassistant`/`\n<think` before scoring).

**Result: 86.7% goal on the 60-task slice** — next to the GGUF's 84.9% on
the full 1000, not next to S3's 99.0%. The regression is in the trained
weights (or the training data), not in quantization, pruning, or the GGUF
rebuild. `hf_diag.py` is not checked in (it lived on the now-deleted pod);
the log is at `baselines/qwen/models/hf_diag.log`.

## 3. A real, separate bug found and fixed along the way

Getting to that diagnostic required fixing something first: the pruned S4
GGUF didn't load at all. `llama_model_load: error loading model: error
loading model hyperparameters: key qwen35.attention.recurrent_layers has
wrong array length; expected 24, got 25`.

`train_s3.sh` (and now `train_s4.sh`, copied forward unchanged) force-sets
`qwen35.block_count` from 25 to 24 to drop the NextN/MTP prediction layer,
but never touches `qwen35.attention.recurrent_layers` — a boolean array
naming which layers are gated-delta vs full-attention, one entry per
layer. That array stays 25 entries. A current llama.cpp validates array
length against `block_count` and refuses to load; an older one (or the
custom `convert_pruned.py` path, which never emits this field at all —
confirmed on S3's own pruned GGUF) didn't. **S1-S3's GGUFs never had this
field and were never exposed to the bug; their scored numbers are
unaffected.** This is new with S4, caught by using a freshly-cloned
llama.cpp for both conversion and inference (§4).

Fixed by rebuilding the file with the array truncated to `block_count`
entries (the extra entry is always the trailing NextN layer — the first 24
of this file's array already formed a clean `[T,T,T,F]×6` pattern matching
`full_attention_interval=4`, confirming which entry was extra).
`baselines/qwen/fix_gguf_layer_arrays.py` is the general form, wired into
`train_s4.sh` after the existing metadata patch so no future run hits this
blind. The fixed pruned GGUF is at
`baselines/qwen/models/qwen3.5-0.8b-s4-pruned-q8-fixed.gguf`.

## 4. Infrastructure notes (skip if you just want the verdict)

The training pod (RunPod secure cloud, 4090, $0.74/hr) trained cleanly in
18h16m. Building the eval environment on it afterward hit a real, external
problem: PyPI's file host (Fastly-fronted `files.pythonhosted.org`) was
reachable for small requests but silently dropped every large transfer —
TCP connection established, zero bytes for 60+ seconds, on every retry —
symptomatic of a PMTU blackhole on that pod's specific network path
(datacenter EUR-IS-2, Iceland). Not fixable from inside the container;
fixed by deleting that pod and creating a fresh one (landed in a US
datacenter), which had no such problem. About $3 and 20 minutes lost
learning that GitHub and Cloudflare were fine, PyPI wasn't — worth knowing
if a future pod session mysteriously hangs on `pip install` of anything
sizeable.

Separately, `llama-cpp-python==0.3.35` from PyPI (pinned since the S1/S2/27B
work) could not load the file even before the array-length bug was found —
it built fine but its vendored llama.cpp snapshot didn't recognize `qwen35`
as an architecture (confirmed it does recognize `qwen35moe` — the two were
evidently added to upstream llama.cpp at different times). Installing from
`git+https://github.com/abetlen/llama-cpp-python.git@main` instead vendors
current llama.cpp and fixed that half of the problem; the array-length bug
was the other half, underneath.

## 5. What this settles, and what it doesn't

**The composites help, confirmed under training, not just in-context.**
R5 showed `MOST`/`LEAST`/`EMPTY` close two failure classes in an untuned
27B's context; this run shows the *trained* 0.8B learned the same lesson —
zero demo abstains, up from S3's 37, with goal success nearly doubling on
that suite. That part of spec 0.4.0 is doing its job.

**Something in this corpus costs the model broadly, and it isn't isolated
to generalization.** E-known — the suite with the least room for a
"learned to generalize worse" story, since it's scored on tasks drawn from
the same distribution as training — dropped 14 points. That is a capacity
or training-recipe problem, not a narrow letters-vs-classic tradeoff by
itself.

**This does not yet tell us whether the typed letters are the cause.** Two
things changed in S4 together: the composites (present in both the typed
and classic corpora equally) and the letters/kinds/enums (typed only). The
broad E-known drop could be the letters costing the small model capacity
to learn binding (R5's predicted risk — "the letters remove a checker
safety net"), or it could be something in this specific corpus/training
run unrelated to letters at all — a data-mix or ordering issue introduced
alongside the composites, independent of the symbol table. **The classic
control corpus is already built** (`data/sft_s4c.jsonl`, same seeds, same
tasks, C-symbols) and untrained. Training it is the one experiment that
separates these: if classic also drops ~10-20 points broadly, the letters
are cleared and something else in S4 is at fault; if classic holds near
S3's numbers, the letters are the cause and typed-symbols.md's claim 2 is
answered — negatively, on this model size and training budget.

## 6. Recommendation

Train the classic control (`train_s4.sh classic`) before touching the
letters/kinds/enums design. It's one more ~18h run (~$14) using
infrastructure and scripts already built and debugged this round. Until
that lands, spec 0.4.0's typed-symbol surface should not ship — R5's
in-context "neutral with reasoning" reading does not survive contact with
an actual small-model retrain, and right now there's no way to tell how
much of the damage is the letters versus something else in the corpus.
