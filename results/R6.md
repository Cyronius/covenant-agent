# R6 — S4 typed 0.8B: the composites/letters corpus regresses broadly

**Date:** 2026-09-10. **Plan:** `.claude/plans/spec-0.4.0.md` §8. **Model:**
Qwen3.5-0.8B, fresh LoRA (r=32, 2 epochs, same recipe as S1-S3) on the S4
typed corpus (`results/logs/gen_s4.sh`, `results/logs/train_s4.sh`) — the
same 62,841-row mix S3 used, rebuilt in the spec 0.4.0 surface (typed
constant letters, string kinds, schema enum constants, `MOST`/`LEAST`/
`EMPTY`). Pod: RunPod RTX 4090, secure cloud. Training: 18h16m, 3,928
steps, no OOM, final train_loss 0.01282 (S3: 0.0117). Cost: training ~$14,
plus ~$3 lost to a dead pod (see §3) and ~$1 for eval — about $18 total.

Every suite except demo requests regressed, several by double digits:

| E-known (`r1_tasks`) | 1000 | **84.9%** | 99.0% | ≥97 | **miss**, −14.1 |
| E-foreign | 500 | **83.8%** | 97.2% | ≥94 | **miss**, −13.4 |
| E-crowded | 300 | **88.0%** | 96.3% | ≥90 | **miss**, −8.3 |
| E-crowded-v2 | 300 | **87.3%** | 92.6% | — | miss, −5.3 |

| e_demo_requests, abstains | 65 | **0** | 37 | <37 | **win** |

One suite improved, and by a lot: demo-request abstention. `MOST`/`LEAST`/
`EMPTY` and the letters together appear to have done exactly what R5
predicted for the composites — the model stopped reflexively aborting on
terse human-phrased requests (0 abstains against S3's 37). Every other
suite — the ones that measure whether the model still does the job right,
not just whether it acts — dropped hard, including E-known, the plainest
in-distribution suite there is, and e_s2_levels, a synthetic abstain
control S3 aced perfectly (240/240) that dropped to 77%.

## 2. Ruled out: this is not the GGUF pipeline

Before trusting these numbers, I checked whether they were an artifact of
my own emergency surgery on the model file (§3). I reloaded the base model
and the LoRA adapter directly through `transformers`/`peft` — no GGUF, no
quantization, no pruning, no hand-rebuilt file — and scored a 60-task slice
of E-known through the same harness (`build` + sandbox), truncating
generation at the first hallucinated turn marker (unconstrained HF
decoding has no grammar to stop it at the program terminator, so it runs
on past `STOP`/`PAUSE` into fake continuation turns — a bug in the
diagnostic script, not the model, worth a full paragraph in case anyone
reruns this: truncate at `\nuser`/`\nassistant`/`\n<think` before scoring).

**Result: 86.7% goal on the 60-task slice** — next to the GGUF's 84.9% on
the full 1000, not next to S3's 99.0%. The regression is in the trained
weights (or the training data), not in quantization, pruning, or the GGUF
rebuild. `hf_diag.py` is not checked in (it lived on the now-deleted pod);
the log is at `baselines/qwen/models/hf_diag.log`.

## 3. A real, separate bug found and fixed along the way

Getting to that diagnostic required fixing something first: the pruned S4
GGUF didn't load at all. `llama_model_load: error loading model: error
loading model hyperparameters: key qwen35.attention.recurrent_layers has
wrong array length; expected 24, got 25`.

`train_s3.sh` (and now `train_s4.sh`, copied forward unchanged) force-sets
`qwen35.block_count` from 25 to 24 to drop the NextN/MTP prediction layer,
but never touches `qwen35.attention.recurrent_layers` — a boolean array
naming which layers are gated-delta vs full-attention, one entry per
layer. That array stays 25 entries. A current llama.cpp validates array
length against `block_count` and refuses to load; an older one (or the
custom `convert_pruned.py` path, which never emits this field at all —
confirmed on S3's own pruned GGUF) didn't. **S1-S3's GGUFs never had this
field and were never exposed to the bug; their scored numbers are
unaffected.** This is new with S4, caught by using a freshly-cloned
llama.cpp for both conversion and inference (§4).

Fixed by rebuilding the file with the array truncated to `block_count`
entries (the extra entry is always the trailing NextN layer — the first 24
of this file's array already formed a clean `[T,T,T,F]×6` pattern matching
`full_attention_interval=4`, confirming which entry was extra).
`baselines/qwen/fix_gguf_layer_arrays.py` is the general form, wired into
`train_s4.sh` after the existing metadata patch so no future run hits this
blind. The fixed pruned GGUF is at
`baselines/qwen/models/qwen3.5-0.8b-s4-pruned-q8-fixed.gguf`.

## 4. Infrastructure notes (skip if you just want the verdict)

The training pod (RunPod secure cloud, 4090, $0.74/hr) trained cleanly in
18h16m. Building the eval environment on it afterward hit a real, external
problem: PyPI's file host (Fastly-fronted `files.pythonhosted.org`) was
reachable for small requests but silently dropped every large transfer —
TCP connection established, zero bytes for 60+ seconds, on every retry —
symptomatic of a PMTU blackhole on that pod's specific network path
(datacenter EUR-IS-2, Iceland). Not fixable from inside the container;
fixed by deleting that pod and creating a fresh one (landed in a US
datacenter), which had no such problem. About $3 and 20 minutes lost
learning that GitHub and Cloudflare were fine, PyPI wasn't — worth knowing
if a future pod session mysteriously hangs on `pip install` of anything
sizeable.

Separately, `llama-cpp-python==0.3.35` from PyPI (pinned since the S1/S2/27B
work) could not load the file even before the array-length bug was found —
it built fine but its vendored llama.cpp snapshot didn't recognize `qwen35`
as an architecture (confirmed it does recognize `qwen35moe` — the two were
evidently added to upstream llama.cpp at different times). Installing from
`git+https://github.com/abetlen/llama-cpp-python.git@main` instead vendors
current llama.cpp and fixed that half of the problem; the array-length bug
was the other half, underneath.

## 5. What this settles, and what it doesn't

**The composites help, confirmed under training, not just in-context.**
R5 showed `MOST`/`LEAST`/`EMPTY` close two failure classes in an untuned
27B's context; this run shows the *trained* 0.8B learned the same lesson —
zero demo abstains, up from S3's 37, with goal success nearly doubling on
that suite. That part of spec 0.4.0 is doing its job.

**Something in this corpus costs the model broadly, and it isn't isolated
to generalization.** E-known — the suite with the least room for a
"learned to generalize worse" story, since it's scored on tasks drawn from
the same distribution as training — dropped 14 points. That is a capacity
or training-recipe problem, not a narrow letters-vs-classic tradeoff by
itself.

**This does not yet tell us whether the typed letters are the cause.** Two
things changed in S4 together: the composites (present in both the typed
and classic corpora equally) and the letters/kinds/enums (typed only). The
broad E-known drop could be the letters costing the small model capacity
to learn binding (R5's predicted risk — "the letters remove a checker
safety net"), or it could be something in this specific corpus/training
run unrelated to letters at all — a data-mix or ordering issue introduced
alongside the composites, independent of the symbol table. **The classic
control corpus is already built** (`data/sft_s4c.jsonl`, same seeds, same
tasks, C-symbols) and untrained. Training it is the one experiment that
separates these: if classic also drops ~10-20 points broadly, the letters
are cleared and something else in S4 is at fault; if classic holds near
S3's numbers, the letters are the cause and typed-symbols.md's claim 2 is
answered — negatively, on this model size and training budget.

## 6. Recommendation

Train the classic control (`train_s4.sh classic`) before touching the
letters/kinds/enums design. It's one more ~18h run (~$14) using
infrastructure and scripts already built and debugged this round. Until
that lands, spec 0.4.0's typed-symbol surface should not ship — R5's
in-context "neutral with reasoning" reading does not survive contact with
an actual small-model retrain, and right now there's no way to tell how
much of the damage is the letters versus something else in the corpus.
