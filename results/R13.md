- **The stages help the planner**: SPt is ahead of A0 on every split, by

  `models/tiny/runs/pod_planner/runs/s6_SPt/best.pt` on

## Two inference-time fixes, both on the laptop, $0

**Only a tool after `CALL`.** 58% of SPt's failed plain programs wrote a
register, constant or field where the grammar requires a tool (`CALL r0`,
`CALL S0`; `call = "CALL" tool {operand}`, `spec/agent_core.md:68`), often
with the rest of the program right. `sample.local_mask` now blocks everything
but the task's own tools there. Plain exam: SPt 56.0 → 58.6%, A0 45.9 →
47.1%. Smaller than the 58% suggested: forced to name a tool, the planner
mostly names the wrong one. `CALL r0` was a symptom of not knowing which
tool, not a slip.

**Best of 4.** If the greedy program does not compile, sample up to three
more at temperature 0.7 and keep the first that compiles (`evaluate.py
--best-of`). Plain 58.6 → 60.7%, decoyed 50.3 → 51.7%. Compile rate on the
plain exam is still only 68%, against 99.9% on the test split.

## What is left: the wrong entity's tool

After the decoding fix (`models/tiny/fail_kinds.py`,
`results/logs/planner/fail_kinds_*_plain_mask.json`), **87% of SPt's failed
plain programs start with a tool of another signature** (A0: 89%), the
failure R12 traced in R9: the request names two entities ("email every
shipper that has a non-hazmat shipment") and the planner starts from the
wrong one. R12 put that down to the missing tool → field links; this run has
them and the failure is still there, now the dominant one. The fix did not
solve it, or something else in this setup is making it worse.

What it is not:

- **Not tool names as a crutch.** Spec 0.8.0 put names on the model-facing
  line, and names are world-specific. But SPt reads opaque-name rows at
  54.3% against named rows' 59.5%, and A0 at 48.6% against 46.8%: hiding the
  names barely matters.
- **Not the look-alikes.** Same-signature picks are under 1% of the plain
  failures.

By level (SPt, plain, with the fix): 0, 13, 16, 17, 18 at 91–100%; the
multi-entity levels collapse, 2 (24%), 3 (19%), 4 (19%), 6 (15%), 9 (18%) and
19 (17%), against R9's 39–62% on the same levels.

## What would tell the causes apart

Every candidate changed between R9 and this run at once: the corpus (S5 →
S6: authored decoys on every training row, uniform twin roles, 15%
opaque-name rows, 120-character descriptions), names on the line, R12's
tokenizer, and the schema-graph fix. Two runs separate them, each about $0.30
on the same pod shape:

1. **A0 on R9's corpus, current code** (R11 §7 item 3, never run): if it
   beats R9's 70%, the graph fix works and S6 is what hurts unseen worlds;
   if it matches R9, the fix does nothing for entity choice.
2. **A0 on S6 without names on the line**: the names check above, done
   properly (trained without, not just hidden at test time).
