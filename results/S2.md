## B4 — vocabulary trim (2026-09-02): PASS

**Change:** drop every token the planner never needs from the tokenizer and
the tied embedding, no retraining. Keep-set = tokens used by the S1 corpus
and every eval prompt (7,864) ∪ 256 byte bases ∪ specials ∪ the result
tokens of the first 40,000 BPE merges (a general-English floor, merge rank
≈ pretraining frequency), closed under merge parents so kept tokens stay
reachable. `baselines/qwen/prune_vocab.py`, `baselines/qwen/convert_pruned.py`.

| | tokens | params | Q8_0 GGUF |
|---|---|---|---|
| S1 (Qwen3.5-0.8B tokenizer) | 248,077 | 752M | 812 MB |
| S1 pruned | **42,263** | **541M** | **578 MB** |

**Faithfulness.** Corpus tokenization identical on 6,000 texts. HF fp32
greedy generations identical 6/6. At Q8_0, pruned vs a GGUF re-converted
from the *same* merge: 36/40 prompts identical; all 4 flips at decisions
whose fp32 top-2 margin was 0.07–0.41 logits (median margin on matching
prompts: 7.75), and in one the pruned model picked the fp32 argmax the
unpruned Q8 missed. Q8 itself jitters by that much — two Q8 conversions of
identical weights (shipped S1 vs re-merged) differ by 3/200 on E-ood.

**Suites (grammar on):**

| E-ood-english (200) | goal | compile | gen p50 / p95 |
|---|---|---|---|
| shipped S1 GGUF | 185 | 197 | 8.4 s / 15.2 s |
| re-merged S1 GGUF (same weights, fresh convert) | 188 | 199 | 8.7 s / 15.3 s |
| **pruned** | **185** | **197** | **5.2 s / 8.9 s** |

| demo suite (65) | goal | compile |
|---|---|---|
| re-merged | 21 | 37 |
| pruned | 20 | 35 |

Pruned sits inside the ±3/200 band that two conversions of identical weights
span, and equals the shipped checkpoint exactly on E-ood. **Rung passes**;
the trim rides into the S2 retrain (Lane C).

**The unplanned win is speed.** The output projection over 248k tokens was
a third of the per-token compute at 0.8B; removing it cuts generation
p50 from 8.7 s to 5.2 s and p95 from 15.3 s to 8.9 s on the dev CPU, same
prompts, same grammar. That is before any Z-ladder work.

**Caveat for real requests:** the English floor is 40k merges; a request
using rarer tokens falls back to smaller kept pieces the model never saw
in that segmentation. The real-session eval slice (B1) is the check.

**Routing histogram** — the frontier agent's calls are the label. A turn is
`generative` if it called generate_image / edit_image / apply_to_lessons,
`knowledge` if it only queried a knowledge base, `read` if it only fetched,
`write` otherwise, `none` if it called nothing. `content_bearing` = a write
whose arguments carry HTML or >160 chars of prose the frontier model wrote.

**Teachability** (what an IR program with a course-builder world + the
writer tool could reproduce):

| class | distinct | eligible | meaning |
|---|---|---|---|
| full | 538 (27%) | 495 | call sequence and arguments are literals the IR carries (ids, names, colours, types) |
| routing | 921 (46%) | 692 | call sequence is expressible; the payload is authored HTML / prose / an image prompt — the writer tool's output, not the planner's |
| abstain | 556 (28%) | 368 | no call: reference is `ABORT AMBIGUOUS` (the frontier asked a clarifying question in most of these) or a plain answer |

The number the plan asked for: **about a quarter of real traffic is fully
expressible today; another half is expressible only as routing into a
writer tool.** The writer tool (A8) is therefore on the critical path for
the majority of real requests, and `ABORT AMBIGUOUS` covers more than a
quarter of turns on its own. Multi-step is 30%, mostly read-then-write
(get_course_theme / get_module_elements → add_element / batch_update_*).

**Tool inventory** (`harness/real_requests.py inventory`, gitignored JSON):
120 tool names; ~25 cover >95% of calls. Nearly every course-builder write
takes `columnId`/`moduleId` ids plus a `props` object (heading, paragraph,
backgroundColor, …) — the IR has no object literal, so the course-builder
world must either flatten the common prop keys into optional STR params or
take `props` as one STR from `write_text`. That is a design decision for the
owner before B2 authoring starts.

**Frozen slice:** `sample --n 250 --seed 20260902` → 250 candidates from
247 sessions (`eval_candidates.jsonl`, `eval_session_ids.json`). Mix:
write 101, none 76, generative 33, read 23, knowledge 17; multi-step 58;
teachability full 63 / routing 111 / abstain 76. Scrub flags: 48 possible
names, 3 URLs, 1 email (replaced). Each row carries `review: {keep, shape,
expressible, notes}` for the human pass. Nothing promotes to
`data/holdout/e_real_sessions.jsonl` before that pass. The S1 baseline run
on the slice waits on the review and on the course-builder world.

**B2 pool:** 1,280 eligible turns outside the frozen sessions
(`b2_pool.jsonl`): full 418, routing 575, abstain 287. With the ~70%
verified-yield assumption that is ~700 authored pairs plus ~290 cheap
abstains, inside the 1,500-pair teacher cap.

**B3 sizing against this histogram.** The converted open sets are the
opposite shape from real traffic: glaive is 64% single READ + 35% abstain,
ToolACE 98% single call and 80% READ, and only hermes is write-heavy
(55%) and multi-call (58%) but yields ~500 usable rows in total. Rule for
the B3 draw (mechanical, no teacher cost): cap at ~1,500 pairs — all usable
hermes (~500), ~400 glaive refusals (the only `ABORT UNSUPPORTED` source),
~400 WRITE/SEND/DELETE-effect rows from glaive + ToolACE, ~200 single
READs chosen for schema diversity (distinct tool-name sets, never the
head). That lands near write 60% / abstain 27% / read 13%, against the
head-sample's 75% read. Multi-step cannot be sourced from open data at
30%; the generator (Lane C) carries it.

**B4 follow-up.** The 42,263-token keep-set was built when 20 sessions had
been pulled. On the full pull the pruned tokenizer splits 1,032 of 1,945
distinct request texts differently from the full tokenizer (decode
identical, zero unknowns): the real texts use 11,035 distinct tokens, and
2,238 of them are not in the pruned vocab. Rebuilt with the full pull as
`merged_s1_pruned_v2_hf` (`results/logs/prune_v2.log`): keep-set 42,263 →
**44,605** (used tokens 7,864 → 15,695; the 40k English floor absorbs most
of the growth), embedding rows 44,608. Tokenization identical on 6,000
corpus texts and on all 1,945 real request texts (was 1,032 different).
Still to do before the trim rides into Lane C: reconvert to GGUF
(`convert_pruned.py`) and rerun the B4 generation-identity checks (40
prompts + demo suite + E-ood) against the re-merged Q8.
