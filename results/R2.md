# R2 — What is the bar to beat?

**Status: IN PROGRESS.** Targets declared below before any evaluation run,
per PLAN §4. Numbers land here as conditions complete.

## Deployment target and success criteria (declared 2026-08-29, before runs)

Owner decision (recorded in PLAN §0/§4): the planner runs in the end-user's
**browser**; parameter budget **0–300M, as small as possible**. R2 is the
accuracy bar to beat, not a kill-switch — Qwen-class 0.5B+ models exceed
the size budget regardless of accuracy.

- **Size:** hard ceiling 300M params (~300 MB INT8 artifact); every halving
  is a product win. Qwen3.5-0.8B ≈ 2.7× over the ceiling.
- **Latency:** p95 ≤ 500 ms end-to-end per task, proxy-measured on the dev
  CPU below until a WASM/WebGPU runtime exists.
- **Memory:** ≤ 500 MB resident during inference.

**Target hardware (proxy):** dev machine CPU — Windows 11 Pro, CPU-only
(no CUDA), llama.cpp (llama-cpp-python 0.3.35) with Q8_0 quantization.
Absolute latencies here are a stand-in; relative accuracy is the durable
result.

## Models (verified current, per PLAN "do not assume")

Smallest Qwen-class instruct models as of 2026-08: **Qwen3.5-0.8B** and
**Qwen3.5-2B** (Qwen3.5 dense lineup, Feb 2026, Apache 2.0), GGUF Q8_0
from unsloth. These fill the plan's ≈0.5B / ≈1.5B slots.

## Conditions

- **A (this file, first):** no fine-tuning; in-context instruction block +
  one worked example + task `input_text` (request + T/F/C tables);
  GBNF grammar constraint (`baselines/qwen/agent_core.gbnf`, derived from
  spec §3 — syntax-level only; binding/typing violations still fall to the
  parser/typechecker, mirroring R3's C2 condition). Deterministic
  (temperature 0). Evaluated on the R1 task set (`data/r1_tasks.jsonl`,
  seed 20260829) for direct comparability with R1's strong-model ceiling
  (99.9% compile / 98.5% goal). PAUSE continuations: model re-prompted
  with executed segment + live register values, max 3 segments.
  An unconstrained arm (same prompt, no grammar) runs on a subset as the
  C1-style reference.
- **B (blocked on cloud GPU, approved):** LoRA on 50k F4 pairs, same
  decoding. Runs after A.

## Results — Condition A (runs of 2026-08-29/30, git 2e62976 + R2 tooling)

| Run | n | parse | compile | goal | gen p50 |
|---|---|---|---|---|---|
| 0.8B, grammar, R1 set | 1000 | 59.7% | 0.4% | **0.2%** | 21.2 s |
| 0.8B, no grammar, subset | 200 | 57.5% | 1.5% | 0.5% | 3.8 s |
| 0.8B, grammar, held-out worlds | 100 | 57.0% | 2.0% | 1.0% | 22.0 s |
| 2B, grammar, subset | 400 | 66.5% | 7.0% | **2.0%** | 39.5 s |

**Condition A is a wipeout at both sizes.** Reference points: R1's strong
model authored the same tasks one-shot at 99.9% compile / 98.5% goal; the
hand-written references run at 100%.

Reading the failure modes (sampled generations + diagnostics):

- Programs are structurally coherent — the models learned the
  list→filter→foreach→call shape from one in-context example — but
  **schema grounding fails**: wrong tool chosen from the table, invented or
  mismatched `F` symbols, missing required args (`tool_valid` 57–66%,
  `arg_valid` 9–18%).
- The syntax grammar barely moves anything at this scale (0.4% vs 1.5%
  compile is noise): the binding/typing/grounding errors it cannot express
  are the whole failure mass. Relevant to H2: **syntax-only constraint
  (C2) is not where the win is; the schema-aware C4 constraint is the one
  that targets what actually kills these models.** parse_ok < 100% under
  the grammar is truncation (48–63% of generations hit the 250-token cap)
  plus indentation/block-pairing rules a CFG can't carry.
- Held-out ≈ known-tool performance, as expected with nothing trained.
- Latency: 21 s (0.8B) / 40 s (2B) per task on the proxy CPU — 40–80×
  over the 500 ms target even before accuracy.

**Interim conclusion:** off-the-shelf in-context use of the smallest
Qwen-class models is a non-starter on this harness. The meaningful bar for
R3 will be **Condition B** (LoRA on 50k F4 pairs) — pending the approved
cloud-GPU run.
