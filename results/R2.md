# R2 — What is the bar to beat?

**Status: IN PROGRESS.** Targets declared below before any evaluation run,
per PLAN §4. Numbers land here as conditions complete.

## Deployment target and success criteria (declared 2026-08-29, before runs)

Owner decision (recorded in PLAN §0/§4): the planner runs in the end-user's
**browser**; parameter budget **0–300M, as small as possible**. R2 is the
accuracy bar to beat, not a kill-switch — Qwen-class 0.5B+ models exceed
the size budget regardless of accuracy.

- **Size:** hard ceiling 300M params (~300 MB INT8 artifact); every halving
  is a product win. Qwen3.5-0.8B ≈ 2.7× over the ceiling.
- **Latency:** p95 ≤ 500 ms end-to-end per task, proxy-measured on the dev
  CPU below until a WASM/WebGPU runtime exists.
- **Memory:** ≤ 500 MB resident during inference.

**Target hardware (proxy):** dev machine CPU — Windows 11 Pro, CPU-only
(no CUDA), llama.cpp (llama-cpp-python 0.3.35) with Q8_0 quantization.
Absolute latencies here are a stand-in; relative accuracy is the durable
result.

## Models (verified current, per PLAN "do not assume")

Smallest Qwen-class instruct models as of 2026-08: **Qwen3.5-0.8B** and
**Qwen3.5-2B** (Qwen3.5 dense lineup, Feb 2026, Apache 2.0), GGUF Q8_0
from unsloth. These fill the plan's ≈0.5B / ≈1.5B slots.

## Conditions

- **A (this file, first):** no fine-tuning; in-context instruction block +
  one worked example + task `input_text` (request + T/F/C tables);
  GBNF grammar constraint (`baselines/qwen/agent_core.gbnf`, derived from
  spec §3 — syntax-level only; binding/typing violations still fall to the
  parser/typechecker, mirroring R3's C2 condition). Deterministic
  (temperature 0). Evaluated on the R1 task set (`data/r1_tasks.jsonl`,
  seed 20260829) for direct comparability with R1's strong-model ceiling
  (99.9% compile / 98.5% goal). PAUSE continuations: model re-prompted
  with executed segment + live register values, max 3 segments.
  An unconstrained arm (same prompt, no grammar) runs on a subset as the
  C1-style reference.
- **B (blocked on cloud GPU, approved):** LoRA on 50k F4 pairs, same
  decoding. Runs after A.

## Results — Condition A (runs of 2026-08-29/30, git 2e62976 + R2 tooling)

| Run | n | parse | compile | goal | gen p50 |
|---|---|---|---|---|---|
| 0.8B, grammar, R1 set | 1000 | 59.7% | 0.4% | **0.2%** | 21.2 s |
| 0.8B, no grammar, subset | 200 | 57.5% | 1.5% | 0.5% | 3.8 s |
| 0.8B, grammar, held-out worlds | 100 | 57.0% | 2.0% | 1.0% | 22.0 s |
| 2B, grammar, subset | 400 | 66.5% | 7.0% | **2.0%** | 39.5 s |

**Condition A is a wipeout at both sizes.** Reference points: R1's strong
model authored the same tasks one-shot at 99.9% compile / 98.5% goal; the
hand-written references run at 100%.

Reading the failure modes (sampled generations + diagnostics):

- Programs are structurally coherent — the models learned the
  list→filter→foreach→call shape from one in-context example — but
  **schema grounding fails**: wrong tool chosen from the table, invented or
  mismatched `F` symbols, missing required args (`tool_valid` 57–66%,
  `arg_valid` 9–18%).
- The syntax grammar barely moves anything at this scale (0.4% vs 1.5%
  compile is noise): the binding/typing/grounding errors it cannot express
  are the whole failure mass. Relevant to H2: **syntax-only constraint
  (C2) is not where the win is; the schema-aware C4 constraint is the one
  that targets what actually kills these models.** parse_ok < 100% under
  the grammar is truncation (48–63% of generations hit the 250-token cap)
  plus indentation/block-pairing rules a CFG can't carry.
- Held-out ≈ known-tool performance, as expected with nothing trained.
- Latency: 21 s (0.8B) / 40 s (2B) per task on the proxy CPU — 40–80×
  over the 500 ms target even before accuracy.

**Interim conclusion:** off-the-shelf in-context use of the smallest
Qwen-class models is a non-starter on this harness. The meaningful bar for
R3 will be **Condition B** (LoRA on 50k F4 pairs) — pending the approved
cloud-GPU run.

## Results — Condition B (0.8B LoRA; runs of 2026-08-30)

Training: LoRA r=32 on all linear projections, 1 epoch over 54,545 SFT
pairs (50k tasks + 4,545 PAUSE continuations with real register state),
RTX 4090, ~4.6 h, final loss 0.011 / token accuracy 99.95%. Merged and
requantized Q8_0 for the same CPU eval harness as Condition A.

| Run | n | parse | compile | goal | gen p50 / p95 |
|---|---|---|---|---|---|
| **0.8B-B, unconstrained, R1 set** | 1000 | 99.9% | 99.4% | **98.5%** | 4.7 s / 8.1 s |
| 0.8B-B, unconstrained, held-out worlds | 100 | 100% | 90.0% | **86.0%** | 3.7 s / 7.5 s |
| 0.8B-B, GBNF grammar, R1 set | 1000 | 100% | 94.7% | 93.9% | 7.9 s / 13.8 s |

By level (unconstrained, full set): 100% on Levels 0–7 and 9;
L8 error-recovery 107/115 (93.0%); L10 PAUSE loops 41/48 (85.4%).

**Findings:**

1. **The tuned 0.8B matches the frontier reference.** R1's strong-model
   ceiling on these exact tasks was 98.5% goal / 99.9% compile; the tuned
   0.8B hits 98.5% / 99.4%. In-distribution, the task is fully learnable
   at 0.8B from synthetic data alone.
2. **After fine-tuning, the syntax grammar hurts instead of helping**
   (93.9% vs 98.5%). Parse rate is ~100% without it — the model
   internalized the syntax — and llama.cpp's grammar sampler masked EOG
   after `PAUSE` under an ambiguous rule, forcing overgeneration that
   zeroed all 48 L10 tasks (fixed in `agent_core.gbnf`, documented there).
   H2-relevant: constraints pay before training convergence, not after;
   R3's value must come from the schema-aware C4 constraint on small/
   undertrained models, not syntax masking on converged ones.
3. **Generalization gap: 12.5 points** (98.5% → 86.0%) on held-out worlds
   and tool families. The model reads schemas well enough to get 86%
   cold, but R5's grounding question is genuinely open below 1B.
4. **Weakest levels are the agentic ones:** error recovery (93%) and
   PAUSE round-trips (85%) — the levels R4's feedback loop targets.

## Decision gate (per the amended PLAN §4)

- Condition B aggregate on Levels 0–8: 99.1% — the accuracy side of the
  old stop-condition is met — but Qwen3.5-0.8B is **2.7× over the 300M
  size ceiling** and **~9× over the 500 ms latency target** (4.7 s p50 on
  the proxy CPU), so the custom-model track continues, exactly as the
  browser-deployment amendment anticipated.
- **The bar R3 must beat is set:** ≥98.5% goal on this task set
  (in-distribution), ≥86% on held-out worlds, at ≤300M params — and every
  halving below that is product value. R3's pass criterion ("some model
  ≤40M reaches the R2 success level on Levels 0–6" under C4) now has a
  concrete number: 100% on Levels 0–6 is what the 0.8B posts there.

## Results — Condition B, 2B arm (2026-08-31)

Same recipe (LoRA r=32, 1 epoch, same 54,545 pairs; 5.5 h on RTX 4090,
final loss 0.0095). Unconstrained decoding only, per the grammar finding.

| Run | n | parse | compile | goal | gen p50 / p95 |
|---|---|---|---|---|---|
| 2B-B, unconstrained, R1 set | 1000 | 100% | 100% | **99.2%** | 7.9 s / 12.2 s |
| 2B-B, unconstrained, held-out | 100 | 100% | 98.0% | **94.0%** | 7.0 s / 14.5 s |

By level (full set): 100% everywhere except L8 error recovery (107/115 —
identical count to the 0.8B). Held-out weak spot is L9 ambiguous scope
(5/9, same as 0.8B); L10 PAUSE goes 48/48 (0.8B: 41/48).

**Scale reading (0.8B → 2B):** in-distribution +0.7 (98.5 → 99.2, above
the frontier reference), held-out +8 (86 → 94). Parameters buy
generalization to unseen schemas far more than they buy in-distribution
accuracy — which is already saturated. L8's residual errors did not move
with scale at all: those tasks are ambiguous-English cases (retry-count
phrasing), not capacity cases.

## R2 conclusions (final)

1. **Bar for R3:** in-distribution 98.5–99.2% goal on this task set;
   held-out 86% (0.8B) / 94% (2B). A custom model at ≤300M must approach
   the in-distribution number; where it lands on held-out grounding is
   the real differentiator (R5).
2. Off-the-shelf zero-shot is a non-starter (0.2–2%); one cheap LoRA
   epoch on synthetic data closes essentially the entire gap. The
   task is data-dominated, not capacity-dominated, at ≥0.8B.
3. Syntax-grammar constraint: useless-to-harmful on converged models;
   R3's constraint value must be measured on small/undertrained models
   (C4, schema-aware) where Condition A shows the failure mass lives.
4. Neither model approaches the browser budget (2.7×/6.7× over size,
   ~9–16× over latency on the proxy CPU). Custom track proceeds.
5. Total Condition B cost: ~$12 GPU across both arms (incl. ~$4.5 of
   debugging waste, documented in CONDITION_B.md).
