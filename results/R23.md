# R23: clutter training fixes cluttered contexts, costs 11 points on clean ones, and barely moves the demo

**Date:** 2026-09-29. **Branch:** `description-reading`. **Spend:** $0.77
(one secure A40, $0.49/hr, two runs side by side, about 1h35m); balance $9.25.
**Plan:** `.claude/plans/demo-clutter-retrain.md`. The owner: "do the run".

## The result

1. **The failure is clutter, and it's measurable off the demo.** R22's best
   model (`fdc25_RD`) on the same 500 unseen-world exam tasks:
   - 87.0% with the constants lists the generator writes;
   - **28.8%** with the demo's kind of list (every person, true/false, all
     statuses worded alike, canned messages, the request as a brief).

   The request and program are identical in both copies; only the constants
   list changed.
2. **Training on cluttered rows fixes most of that.** Two seeds of the same
   recipe on the cluttered corpus (`clt_RD`, `clt_RDs1`):
   - cluttered exam: **66.2 / 66.4%** on the 500-task sample (fdc25_RD
     28.8%); 61.6 / 63.8% greedy on the full 2,000-task half, 66.6 / 67.8%
     with backoff.
3. **It costs the clean exams, and both seeds agree:**

   | exam | `fdc25_RD` (R22) | `clt_RD` | `clt_RDs1` |
   |---|---|---|---|
   | plain | 79.5 | 67.0 | 69.1 |
   | plain + backoff | 84.0 | 72.2 | 73.6 |
   | decoyed | 51.4 | 47.1 | 46.6 |
   | flip probe | 45.8 | 39.6 | 35.2 |
   | test (own corpus) | 94.5 | 89.6 | 90.6 |
   | 500 sample, clean (play.py, backoff) | 87.0 | 73.4 | 74.2 |
   | 500 sample, cluttered (play.py, backoff) | 28.8 | 66.2 | 66.4 |

   Some of the plain drop is the wording leak going away: in the plain exam,
   the enum value the program uses is still worded differently from the
   others, and the old model learned to read that. But the losses are
   broader than that (see below).
4. **The demo moves from 5/70 to 10/70 (14.3%), both seeds.** One more request
   ("list all the cards") now works in all five orderings. The fine-tuned
   Qwen 0.8B gets 43–48%. The demo's remaining failures are mostly not
   clutter any more.

## Why the demo is still failing

The 14 demo requests fail on things the generator never produces:

- **People named by first name, in lower case.** "delete all the cards owned
  by bob", "assign card 6 to Bob": the constant is "Bob Alvarez", and the
  planner picks another user. In the cluttered corpus, every request that
  names a multi-word record uses the full name verbatim (1,583 of 1,583
  sampled). The planner has never had to match "bob" to "Bob Alvarez".
- **Records named by part of their title.** "move the release notes to doing
  column" → the constant is "card 2 — Write release notes for v4.2"; the
  planner answers `ABORT AMBIGUOUS`. Same for "the race condition issue".
- **Demo-only request shapes:** "duplicate the release notes issue" (FORMAT
  plus create), "tell bob which of his cards are overdue" (write text, then
  send), "create a new issue … in done column" (create, then set status).
  These are single hand-written tasks; the generator has no recipe that
  makes them.
- Some filter-stuffing is still there ("archive everything that is done"
  adds a membership test; "let's delete the oldest issue" adds a status
  filter), but it's no longer the main failure.

## What was lost on the clean exam

Over the 500-task clean sample, `clt_RD` loses 88 tasks `fdc25_RD` gets and
wins 20. Of 60 losses inspected:
- 18 have the same tools and constants as the old model's program and
  differ in a field or the order of steps;
- 11 differ only in which constant;
- the rest differ in tools, some with extra constants in a filter and some
  with fewer.

Losses are spread over all levels. In-distribution accuracy fell too (test
94.5 → ~90), so the cluttered rows are harder to learn in 12 epochs. This
isn't only the old model losing a shortcut.

## Terms

- **Clutter** (`data.gen --clutter`, `data/gen/clutter.py`), per row:
  every enum value worded one way (eight styles, one of them the demo's "the
  done status"); 1–5 records the request doesn't name added as IDs (70% of
  rows); true/false (50%); 1–5 canned messages (50%) and the request as a
  brief (40%), added only to rows with no text of that kind; then the list is
  shuffled.
- **Corpus:** fdc25's 30,000 rows exactly (same seeds, same 25% flip-decoy /
  75% options-off mix), all cluttered. Same ids and requests as fdc25 on
  every row checked.
- **Cluttered exam (`+clut`):** the plain exam's 4,000 tasks regenerated
  with `--clutter`; all 4,000 have the plain exam's ids, requests and call
  sequences.
- **500 samples:** every 8th task of the plain exam and its cluttered copy,
  run through `play.py` (the demo's own loop, live Ternlight reader,
  backoff 3), so the old and new models are measured the same way.

## Next (for the owner)

1. **Partial names in the generator.** Requests that call a person by first
   name, lower case, or a nickname, and a record by a fragment of its title
   ("the release notes"), with the constant still carrying the full name.
   This is what the demo's people and cards need, and no row has it now.
2. **Mix cluttered and clean rows** (e.g. 50/50) instead of cluttering every
   row, to buy back the clean-exam points. Clutter at 100% was the simplest
   test of the cause, not a tuned rate.
3. Both need one more pod run, about $0.80.

## Caveats

- The demo suite is 14 distinct requests in five constant orderings. 10/70
  is two requests, so it can't separate small differences; the 500-task
  samples and full exam halves are the numbers to trust.
- The plain, decoyed and flip exams keep the wording leak (the used enum
  value worded differently). A model that doesn't read it is at a
  disadvantage there that says nothing about real use.
- `fdc25_RD`'s full-exam numbers are R22's greedy/backoff runs, from
  evaluate.py; the 500 samples are play.py. Compare within each row of the
  table, not across rows.
