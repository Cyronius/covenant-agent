# R4 — reactive execution and the design-tax ladder on Qwen3.8-27B

**Date:** 2026-09-08. **Plan:** `.claude/plans/reactive-execution.md`
(§7 steps 1–2). **Model:** Qwen3.8-27B UD-IQ3_S, untuned, in-context,
per-task grammar, greedy, 0-shot. **Tasks:** the 25-task slice of
`results/S2.md` (7 E-known, 10 demo requests, 8 `e_crowded_v2`), scored on
final state. **Hardware:** a RunPod RTX 5090 (`results/logs/pod_27b_setup.sh`;
2.2 s per one-shot task against 264 s on the dev CPU).

## 2. Reactive execution: the rule never fires

**Zero runtime errors in 150 task-runs.** The plan's §2B — a segment that
raises returns to the planner with `RUNTIME <code> line:<n>`, its calls, and
its bound registers — is built (`harness/run.py react_on_error`, spec 0.3.1
§4/§9, 11 tests) and had nothing to act on. On this model the typechecker
intercepts everything before execution: the Cyrus program's `SELECT 0` on an
empty match dies as a `TYPE_ERROR`, not an `INDEX_OUT_OF_RANGE`. `compile_ok`
equals `goal_success` on every slice of the k0/prompt/react arms — every
failure is static — and with K2 repair in front the survivors are wrong
programs, not raising ones. Runtime errors are the small model's failure
mode (S3's `e_crowded` rows), not the 27B's; the rule stays in the harness
for the retrain and costs nothing when it does not fire.

**The observe-then-decide paragraph costs 4 tasks (17 → 13) and produces one
PAUSE.** Told to decide after seeing values, the model did not pause; it
tried to *anticipate* the observation in one shot:

```
FILTER r0 F0 EQ C0 AND F6 LT NOW -> r1
IF r1 EQ C6            <- "if nothing matched": a LIST compared to a BOOL
  CALL T4 C0 C10
ELSE
  CALL T0 C15 r1 -> r2
```

`demo_10_s4`, `demo_10_s1` (both `TYPE_ERROR line:3 LIST OBJ:card BOOL`),
`kanban_L3` (an empty `IF` arm), `kanban_L5` (a direct `CALL T1 C1` lookup
replaced by list → filter → select, mistyped), `driving_school_L9` (`ABORT
NEEDS_INFO C0` on a task it had solved). One task gained (`freight_forwarding`,
whose K0 program was an `IF C1 EQ C1` hedge). The one PAUSE (`winery_L10`)
was followed by a continuation that `GET`s a field off a list. With K2 the
same arm loops: `winery_L10` pauses three times, then five under `--react`'s
wider segment bound, and exhausts.

This is the third prompt-taught behaviour to fail the same way (tool
descriptions for rejection, the check-then-decline paragraph, now PAUSE):
the 27B honours the *shape* the paragraph names by writing it into the
one-shot program, and the IR cannot express "is this list empty" without a
`COUNT` and a numeric constant the task does not carry. **PAUSE has to come
from the corpus** (plan §6), where the reference observes and the
continuation is a separate row. The harness side is ready for that.

## 3. Rung 1: `<think>` is worth 3 tasks and all but one compile error

Two-phase decode (`run_a.py --think 1024`): the model reasons freely in its
own `<think>` block, then the grammar-constrained program follows with that
reasoning in context. Same K0 prompt, same grammar.

- **17 → 20/25; compile 18 → 24/25.** Both `demo_11` type errors (the
  `TIME ← BOOL` / `TIME ← ID:user` class, of which the typed grammar fixed
  one) are gone: the model works out the argument order before it writes
  the line. `freight_forwarding` and `crm_L4`'s static errors are gone too.
- **It pauses where the reference pauses.** `winery_L10` ("check in first")
  and `golf_club_L10` ("report back to me, then cancel") — the two L10
  tasks whose references PAUSE — are the two tasks it paused on, unprompted.
  The reasoning names the rule it used: "PAUSE when the request says to
  report back before acting". The paragraph could not buy that; 300 tokens
  of the model's own planning did.
- **Cost:** p50 latency 2.2 s → 4.8 s (demo) / 8.1 s (known) / 12.2 s
  (crowded) on the GPU; tokens out p50 37–50 → 280–780. On the dev CPU that
  would be 15–40 minutes per task. K2 adds nothing on top (the one remaining
  static error does not repair).

The five that remain, with the reasoning read (`row["think"]`):

| task | what happened | class |
|---|---|---|
| `kanban_L4`, `crm_L4` | "message the user with the most overdue cards": the reference is a 14-line `FOREACH`/`COUNT`/`IF`/`LET` argmax; the model concludes "there's no GROUP BY / COUNT per assignee" and `ABORT UNSUPPORTED` | **expressiveness perception** — the IR can do it, the idiom is not visible |
| `demo_12_s1` | "make cyrus the owner": abstains, `NEEDS_INFO F10` (no value for the assignee) vs reference `NOT_FOUND` (no Cyrus constant to check against) | reason taxonomy; the abstention itself is right |
| `winery_L10` | PAUSEs correctly, then the continuation messages each vineyard twice (`C1`, then a `FORMAT`ed copy) | continuation semantics |
| `golf_club_L10` | PAUSEs correctly, then `CALL T12 r2.F96 C0` (set status ← a TIME) instead of `T15` cancel | symbol choice; `TYPE_ERROR line:2 STR TIME` |

Two of five are a single IR gap: **argmax-by-count has no idiom**. A
thinking 27B will not discover the reference's loop; a `GROUP`/`ARGMAX`
primitive (or a `COUNT`-per-key form) is the rung-3-sized change this
points at.

## 4. What the ladder says so far

| rung | condition | /25 | delta |
|---|---|---|---|
| K0 | one-shot, no reasoning, T/F/C symbols, positional args | 17 | — |
| K2 | + static repair | 19 | +2 |
| 4 | + reactive (prompt-taught PAUSE, runtime error as a turn) | 13–14 | **−4** |
| 1 | + `<think>` | 20 | **+3** |
| 2, 3, 0 | real names, named args, traditional agent | not run | |

The decoder-side levers are done: the reasoning ban is the one constraint
that measurably costs the big model, and it is the one the 0.8B cannot lift
(no reasoning budget in the browser). Rung 4 as a prompt is negative; as a
corpus change it is untested. The next measurements are rung 2 (real names:
grammar + prompt, one pod-hour) and rung 0 (the agent ceiling the owner
expects at ~25/25 — until it is measured, "the design costs 5–8 tasks" is
the claim, not the finding).
